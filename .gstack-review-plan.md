## Step 0: Nuclear Scope Challenge

### 0A. Premise Challenge

**Is this the right problem?** The user wants Project Memory to be callable as a DSH subagent via `use_agent(agent: "project-memory")`. Currently it's not — `install.ps1` installs the agent file to Claude/OpenCode/Codex paths but NOT to `~/.dsh/agents/`. So the registry can't find it even if installed.

**What would happen if we did nothing?** Project Memory remains callable only via the orchestrator agent in Claude/OpenCode/Codex. DSH users get skills but can't dispatch the orchestrator as a focused subagent. Fine for now, blocks the "project memory sub-agent" vision.

**Is the plan the most direct path?** Almost. But there's a missing step: install.ps1 must also copy `project-memory.md` into `~/.dsh/agents/`. Without that, the registry has nothing to register.

### 0B. Existing Code Leverage

- `agents/project-memory.md` already exists with `mode: subagent` frontmatter — it's ready to go
- `install.ps1` already has `Install-Agent` function — needs one more destination
- `dsh-plugin/cordis.patch.yml` already has independent IDs — no merge risk
- `@aiwayds/dsh-subagent-registry` v0.8.1 is published and stable

### 0C. Dream State Mapping

```
CURRENT STATE                          THIS PLAN                       12-MONTH IDEAL
install.ps1 installs to                + registry as dep               DSH users run:
Claude/OpenCode/Codex paths            + copies to ~/.dsh/agents/      use_agent("project-memory", "compound my last task")
DSH plugin loads skills                + subagent-registry loads       → focused memory agent runs,
Project Memory skills available          agent file                     then returns compounded knowledge
DSH CANNOT call project-memory         → seamless subagent dispatch  (all in one command)
as subagent
```

### 0C-bis. Implementation Alternatives

**APPROACH A: Bundle as npm dependency (recommended)**
- Add `@aiwayds/dsh-subagent-registry` to `dependencies`
- Add its cordis.patch.yml entry to our patch
- Copy `project-memory.md` to `~/.dsh/agents/` in install.ps1
- Users get everything with one `dsh plugin add`

**APPROACH B: Separate installation + install.ps1 copies agent file**
- Don't add dependency
- Update install.ps1 to also install to `~/.dsh/agents/`
- Document that users need to separately add the registry
- Two commands, but zero coupling risk

**APPROACH C: Bundle as optional peer dependency**
- Add to `peerDependencies` with `optional: true`
- Plugin detects if registry is present and auto-configures
- Best of both worlds but more complex logic

**RECOMMENDATION: Approach A** — one dependency is fine for a focused plugin. The registry is stable (v0.8.1), MIT licensed, same pattern as our `dsh-skill-filesystem` dep. Reduces user friction significantly.
